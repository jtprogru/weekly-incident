Новый слой не должен обещать восстановление данных, которые никогда не были собраны.

## 2. Границы задачи

Различать четыре сущности:

1. **Запись источника** — объект с идентификатором в пространстве конкретной статусной страницы или фида.
2. **Версия записи** — содержимое этой записи в момент обнаруженного изменения.
3. **Канонический инцидент** — одна установленная сущность, к которой могут относиться несколько записей источника.
4. **Редакционная история** — связанные инциденты, например авария облака и последствия у клиентов.

Первая версия решает сопоставление внутри одного вендора. Межвендорские связи допускаются как редакционные отношения с доказательствами, но не уменьшают число инцидентов и не объединяют их скоры. Совпадение времени не доказывает общей причины.

В первую версию не входят LLM, embeddings, база данных, сетевое разрешение URL, извлечение реального начала аварии из прозы и изменение самой формулы скоринга. Сопоставление и рендер работают offline. Временные и текстовые пороги подбираются по размеченным примерам; готовых универсальных порогов точности сейчас нет.

## 3. Архитектурное решение

Добавить слой identity resolution между архивом источников и недельным представлением:

```text
collect → парсеры → версии записей + совместимый недельный архив
                           ↓
              полный локальный набор записей
                           ↓
        признаки → кандидаты → правила + ручные решения
                           ↓
                 реестр идентичности
                           ↓
              канонические инциденты
                           ↓
             выбор недели → score → render
```

Реестр идентичности — долговечное состояние. Канонические JSON, индексы, отчёты и выпуски — производные данные. Одинаковые архив, реестр, решения, версия правил, конфигурация и `-now` должны давать побайтово одинаковый результат.

| Вариант | Польза | Цена и ограничения | Решение |
| --- | --- | --- | --- |
| Исправить только AWS-парсер | Небольшое изменение | Не решает исторические дубли, перенос недели, несколько ID одного события | Использовать отдельные улучшения парсера внутри общего решения |
| Удалять дубли при записи | Простой потребитель архива | Ошибка объединения уничтожает доступные свидетельства; сложный откат | Не использовать |
| Группировать по заголовку и времени в рендере | Быстрый прототип | Ложные объединения, разные результаты у collect и digest, нет устойчивой идентичности | Только признаки для кандидатов |
| Реестр связей и производное представление | Объяснимость, отмена, стабильные ссылки, общий путь для всех вендоров | Новые схемы, проверки согласованности и миграция | Основной вариант |

Цена решения — поддержка небольшого объёма состояния помимо исходного архива. Сначала реализуется read-only аудит; запись реестра и изменение выпусков добавляются отдельными этапами.

## 4. Инварианты

- Исчезновение из фида не удаляет запись, версию или связь.
- Каждый source record принадлежит ровно одному активному каноническому инциденту; спорные записи остаются самостоятельными до решения.
- Неизвестное время, severity или регион не превращаются в известные при объединении.
- Путь недельного файла, заголовок и дата начала не определяют идентичность.
- Стабильность ID источника считается свойством конкретного адаптера, а не следствием наличия `NativeID`.
- Общий URL статусной страницы не является ключом события.
- Одно совпадение шаблонного текста не является достаточным основанием объединения.
- Ручное `different_incident` запрещает объединение соответствующих групп, в том числе через промежуточную запись.
- История изменений, причина решения и происхождение выбранных полей доступны для проверки.
- Одинаковый повторный вход не создаёт новых версий и не переписывает файлы из-за времени запуска.
- `collect` и `digest` используют один builder канонического представления и одну версию правил.
- Неоднозначность сопоставления видна в отчёте; она не маскируется пропуском записей.

## 5. Модель данных и хранение

Названия ниже — предлагаемый контракт. Уточнить Go-типы на этапе реализации схем, сохранив описанную семантику.

### 5.1. Записи и версии

Ввести `SourceRef = source_id + native_id`. `source_id` обозначает конкретный логический источник; сейчас его можно первоначально связать с `vendor` из конфигурации. Если у вендора появятся несколько страниц, дать им разные `source_id`. Смена домена той же страницы оформляется явным alias источника. Поле `vendor` продолжает использоваться для редакционного веса.

Существующий `key` сохраняется как legacy-ссылка. Для AWS он идентифицирует наблюдаемую цепочку, а не гарантированно уникальное событие. Не менять старые AWS-ключи массово.

Для production-этапа добавить сохранение версий только при изменении содержимого:

| Артефакт | Назначение |
| --- | --- |
| `data/observations/<source_id>/<content_hash>.json` | Неизменяемый снимок нормализованной записи и её `raw` |
| `data/observations/manifest.json` | История ревизий source record, ссылки на снимки, текущая ревизия и время обнаруженного изменения |
| `data/YYYY/Wnn/<vendor>.json` | Совместимое представление последних записей для существующих потребителей |

Хеш вычислять из канонически сериализованного содержимого с версией схемы и пространством источника, исключая служебное время наблюдения. Проверять содержимое при совпадении хеша. Новое время polling не создаёт ревизию. Последовательность содержимого A → B → A создаёт три ревизии, но только два уникальных снимка: возврат к старому содержимому тоже изменение.

Время обнаруженного изменения не выдавать за время редактирования у вендора. В manifest хранить монотонный номер ревизии source record, чтобы одинаковый `-now` не делал порядок неоднозначным. Исправления текста обновления сохраняются как версии, а не как два независимых сообщения timeline.

При bootstrap импортировать текущее дерево архива. Для старых записей порядок прежних версий неизвестен: не выводить его из имени файла, `FirstSeenAt` или длины timeline. Восстановление дополнительных версий из Git — отдельный необязательный импорт с указанием commit и ограничений истории.

### 5.2. Реестр идентичности

Предлагаемый файл: `data/identity/registry.json`.

Хранить `schema_version`, активные canonical IDs, членство source records, alias прежних canonical IDs и журнал операций merge/split. У каждой операции — `decision_id`, тип основания, версия правила и ссылки на evidence. Снимок реестра входит в набор входов для воспроизведения.

Canonical ID назначается один раз. Для первого импорта использовать детерминированный anchor из отсортированных `SourceRef` и версионированную hash-схему. После регистрации anchor фиксируется: обнаружение более ранней записи не пересчитывает ID.

Правила жизненного цикла:

- Новая самостоятельная запись получает собственный ID.
- Новая запись подтверждённого события присоединяется к существующему ID.
- При merge уже зарегистрированных групп выбирается один сохраняемый ID по фиксированному порядку; остальные остаются aliases.
- При split группа с прежним anchor сохраняет ID, другие получают новые ID. Alias, который после split нельзя разрешить однозначно, помечается как неоднозначный; запрещено незаметно направлять его в произвольную группу.
- Ни один выданный ID не переиспользуется для другого события. Полная пересборка требует сохранённого реестра или его журнала; повторная генерация только из текущих данных не обещает тех же исторических ID.

Нельзя сохранять просто номер строки или hash текущего состава группы: оба изменяются при добавлении участников.

### 5.3. Решения редактора

Предлагаемый файл: `dedup/decisions.yaml`, вне автоматически создаваемого `data/`. Это декларативный вход, который можно редактировать и проверять через обычный diff.

Типы решений:

| Тип | Значение |
| --- | --- |
| `same_incident` | Указанные записи описывают один инцидент |
| `different_incident` | Указанные записи не должны оказаться в одной группе |
| `field_override` | Выбор значения спорного поля с основанием |
| `related_incidents` | Редакционная связь без дедупликации; отдельный последующий этап |

Обязательные атрибуты: стабильный ID решения, ссылки на source records, причина, evidence, автор решения и дата. Автор задаётся явно, не выдумывается сборщиком. Для замены решения использовать `supersedes`, сохраняя историю. Для спорного поля привязывать override к конкретной версии/evidence; при существенном изменении входа поднимать повторную проверку.

Ссылки не должны зависеть только от пути недельного файла. Проверять существование участников, конфликтующие активные решения, циклы aliases и соответствие пространству источника. Ошибка такого входа блокирует применение нового канонического результата с понятной диагностикой.

### 5.4. Производное представление

Предлагаемые артефакты:

- `data/canonical/incidents.json` — канонические поля, участники, уникальные обновления и provenance.
- `data/canonical/manifest.json` — fingerprint входов, версии схем/правил, хеш решений и реестра.
- `reports/dedup/` — отчёт кандидатов и сравнение старого и нового представлений; путь задаётся явно, отчёты не коммитятся ежедневным workflow по умолчанию.

У канонического инцидента хранить `canonical_id`, `vendor`, `members`, `source_urls`, выбранные поля, `field_provenance`, `conflicts` и качество времени (`vendor_reported`, `first_observed_update`, `unknown`). Производное представление не выдавать за новый payload вендора и не записывать в его `raw`.

## 6. Алгоритм сопоставления

### 6.1. Подготовка признаков

Читать все vendor-файлы архива, исключая индексы и новые служебные каталоги. Выполнять сопоставление глобально, до фильтра недели. Для текущего размера достаточно полного локального прохода с индексами в памяти; необходимость постоянной БД не установлена.

Для каждой записи извлечь:

- `SourceRef`, legacy key и признак стабильности ID;
- URL конкретного события и признак его пригодности для identity;
- ID обновлений в правильном пространстве источника;
- точные fingerprints обновлений: UTC-время и консервативно нормализованный текст;
- заголовок, компоненты, регионы, наблюдаемое временное окно;
- признаки завершения, повторного открытия, исправлений и неполноты истории.

Для точного fingerprint допустимы нормализация перевода строк и краевых пробелов. Не удалять числа, названия регионов, отрицания, даты и смысловую пунктуацию. Более агрессивные признаки допускаются только для поиска кандидатов. Оригинал всегда доступен. Пустые и шаблонные сообщения не использовать как самостоятельное доказательство.

Нормализация URL выполняется offline и по правилам адаптера. Не отбрасывать произвольные query parameters: они могут содержать идентификатор. Не считать редирект или два разных домена эквивалентными без зарегистрированного правила.

### 6.2. Генерация кандидатов

Сначала индексировать точные совпадения `SourceRef`, event URL и fingerprints обновлений. Они проверяются по всему архиву без ограничения одной неделей.

В реализованной первой версии используются точные признаки внутри одного вендора. Нечёткий поиск по близости начала, компонентам и заголовкам остаётся последующим расширением после независимой разметки; временные и текстовые пороги для него сейчас не задаются.

Не трактовать `resolved_at = null` как бесконечное окно для поиска дубликатов: устаревшее `investigating` иначе будет совпадать со всеми последующими авариями. Для candidate generation использовать диапазон известных обновлений и отдельную политику для неполных данных.

### 6.3. Правила принятия решения

| Сигнал | Действие первой версии |
| --- | --- |
| Тот же стабильный `SourceRef` | Версии одной записи; проверить целостность пространства ID |
| Один event URL у источника с подтверждённой уникальностью ссылок | Кандидат; auto-merge включать только после fixtures этого адаптера |
| Общие update IDs с подтверждённой семантикой | Сильный кандидат; проверить область уникальности и противоречия |
| AWS: несколько точных общих нетривиальных обновлений одной service-region цепочки | Первоначально кандидат; после проверки эталонов разрешить узкое автоматическое правило |
| Один шаблонный update, похожий заголовок, близкое время | Только кандидат на ручную проверку |
| Явное `same_incident` без конфликтов | Объединение с ручным основанием |
| `different_incident`, конфликт identity или несовместимые свидетельства | Запрет объединения / конфликт для разбора |

Не подменять объяснимые основания числом «вероятность 95%», пока нет калиброванной модели. Использовать уровни `exact_identity`, `strong_evidence`, `review_required`, `conflict`; это категории доказательств, не вероятности.

Решение принимается для целой группы. Перед присоединением B к группе A проверять ограничения всех участников. Не делать connected components по нечётким рёбрам: A похож на B, B похож на C ещё не означает A = C. Если одна запись подходит к двум несовместимым группам, сохранить её отдельно и вывести неоднозначность.

Сортировать кандидатов и операции с полным tie-breaker. Изменение порядка файлов, входных записей или map iteration не меняет итог. Повышение версии правил не отменяет молча подтверждённые связи: сначала формируется diff решений, затем применяется переход.

### 6.4. Особенности адаптеров

Для Statuspage, Slack, GCP и Yandex Cloud проверить по текущим парсерам и fixtures семантику incident/update IDs. Зафиксировать capability каждого адаптера, не объявлять все поля с именем `id` глобально уникальными.

Для AWS:

- Сохранить RSS item GUID как идентификатор обновления с проверенной областью уникальности, если он доступен; не считать его ID инцидента.
- Для исторических данных извлекать признаки из существующего `raw` через адаптер, без ручного изменения vendor JSON.
- При отсутствии GUID использовать точный fingerprint сообщения и время.
- Проверять service-region, порядок обновлений, маркеры завершения и последующего нового события.
- Не переносить порог разрыва цепочки из парсера автоматически в правило дедупликации: это разные решения.
- Если две версии не имеют общих сообщений из-за полного сдвига окна, не объединять их только по сервису и близости времени.
- Сначала подтвердить правило на найденной паре и отрицательных примерах; только затем включать auto-merge.

## 7. Построение канонических полей

Дедупликация identity и выбор значений полей — отдельные операции. Установленная идентичность не устраняет конфликт дат или статусов.

| Поле | Правило |
| --- | --- |
| Начало | Для стабильного источника учитывать явные исправления в последней известной версии. Для усечённых AWS-цепочек брать самое раннее сохранённое наблюдаемое обновление, сохраняя качество `first_observed_update` |
| Завершение и status | Использовать доказанный порядок версий/обновлений. Не брать безусловный максимум статуса; повторное открытие может следовать за resolved |
| Duration | Пересчитать по выбранным границам; не складывать длительности записей. Конец раньше начала — конфликт до pinned-решения о неизвестной длительности; даты не придумывать |
| Components | В текущей модели это отображаемые имена: сохранять исходную кратность и provenance к snapshot с vendor IDs в raw. Имя не является идентификатором. Разные списки нескольких источников требуют override; для версий одной записи брать актуальный список |
| Impact | Сохранить семантику адаптера; не повышать `unknown` из-за наличия дубля. При противоречии использовать явный порядок версий или ручное решение |
| Title | Выбранная актуальная версия с provenance; не влияет на identity |
| URLs | Все ссылки на свидетельства плюс предпочтительная ссылка для рендера |
| Timeline | Уникальные сообщения в стабильном порядке; исправления одного сообщения показаны как ревизии, а не новые события |
| FirstSeenAt | Самое раннее известное наблюдение участников; не использовать как время исправления payload |

Для timelines сначала сопоставлять сообщения по надёжному update ID; без него объединять только точные совпадения времени и нормализованного текста в допустимом пространстве источника. Одинаковый ID с изменившимся body сохраняет обе версии и известный порядок. Одинаковое время с разным текстом без надёжного ID не схлопывается автоматически.

Для AWS объединение наборов сообщений должно сохранять ранее собранные updates при усечении фида. Для полных snapshots других источников отсутствие сообщения может иметь другую семантику: хранить версии, а политику отображения задавать адаптером.

Если порядок конфликтующих исторических версий неизвестен, не выбирать значение по длине записи или `FirstSeenAt`. Сохранить конфликт и потребовать явный выбор для полей, влияющих на score. До разрешения такого конфликта новый результат остаётся в shadow-режиме, а рабочий выпуск сохраняет прежнюю семантику. Самостоятельные непроверенные кандидаты при этом продолжают учитываться отдельно.

Существующая формула `duration_minutes × max(1, component_count) × vendor_weight` применяется один раз к итоговому инциденту. Вес, threshold и отношение OR между длительностью и impact не меняются. Устаревшее AWS `investigating` остаётся известным ограничением; дедупликация сама по себе не доказывает завершение аварии.

## 8. Недели, индексы и рендер

Для source archive устранить зависимость поиска identity от недели: перед upsert строить глобальный индекс `SourceRef → место хранения`. Уже известную запись обновлять в её существующем файле, даже если `StartedAt` исправлен. Это сохраняет upsert-only и не требует удаления старого файла. Путь становится местом хранения, а семантическая неделя определяется полем начала.

Для новых записей по-прежнему выбирать физический файл по начальному `StartedAt`. Загрузчики старого режима после этого также должны выбирать неделю по данным из глобального чтения, иначе перенос начала продолжит давать неверный выпуск. Документировать изменение семантики путей в README и PLAN.

Если bootstrap найдёт одинаковый source key в разных файлах, зарегистрировать обе версии с provenance. При различающемся содержимом и неизвестном порядке поднять конфликт; не выбирать победителя лексикографически. Автоматическое физическое удаление таких записей не входит в миграцию.

Канонический инцидент попадает в ISO-неделю его выбранного начала в UTC. Он учитывается один раз во всём архиве. Многонедельный инцидент не размножается по неделям; отдельное представление «активен на этой неделе» может быть будущей функцией.

Общий builder получает полный локальный набор, реестр, решения и фиксированное время, затем возвращает канонические инциденты и затронутые недели. Пересчитывать объединение старой и новой недель участников и канонического начала. Неделя, из которой ушёл последний инцидент, тоже пересобирается в корректный пустой индекс.

На первом этапе допустим пересчёт всех недель в памяти с записью только изменившихся файлов. Оптимизацию touched weeks добавлять после проверки корректности, без предположения, что `stats.Weeks` исходного upsert покрывает все изменения identity.

Индекс и render получают одни и те же canonical IDs. Не подставлять canonical ID в `NativeID` и не запускать `Finalize()` так, чтобы он снова превратился в `vendor/native_id`. Предпочтительно ввести явный тип для канонического представления и входа скоринга.

В `digest.md` показывать canonical ID/якорь, число исходных записей, ссылки на них, основание объединения и предупреждения. В `brief.md` использовать тот же timeline. В `summary.txt` показывать краткую статистику и ссылку на детали без перегрузки техническими полями.

Счётчики определить явно:

- `source_records_total` — число логических source records, без повторного счёта версий.
- `source_versions_total` — число сохранённых ревизий, отдельно от инцидентов.
- `canonical_incidents_total` — число групп после подтверждённых объединений, включая самостоятельные записи.
- `merged_source_records_total = source_records_total - canonical_incidents_total` для полного набора при одном членстве каждого source record.
- `pending_candidate_pairs` — число пар на проверке; не трактовать как число дополнительных дубликатов.
- `conflicted_groups_total` — число групп с неразрешёнными конфликтами.

В недельных отчётах `source_records_total` означает участников канонических инцидентов выбранной недели, а не количество строк физических файлов этой недели. Отдельно можно показывать физические строки для аудита миграции. `SourceStatus.IncidentsSeen` остаётся числом нормализованных записей, полученных при сборе; переименовать подпись при необходимости, но не подменять его canonical count.

## 9. CLI, конфигурация и режимы

Реализована команда `cmd/dedup` со следующими действиями. Примеры запуска и recovery приведены в DEDUPLICATION.md.

| Действие | Входы и результат | Запись |
| --- | --- | --- |
| `audit` | Полный архив → кандидаты, evidence, конфликты, статистика | Только явно заданный каталог отчёта |
| `validate` | Проверка схем, реестра и ручных решений | Не изменяет входы |
| `plan` | Текущий реестр + решения + правила → предлагаемый diff identity и недель | Только отчёт |
| `apply` | Проверенный план с fingerprints → новый реестр и derived data | Явная операция, отказывает при изменившихся входах |
| `rebuild` | Архив + сохранённый реестр + решения → canonical data и индексы | Производные файлы; не изменяет решения identity |

Параметры: пути данных, конфигурации, решений и отчётов, а также `-now`. Любая новая команда должна принимать временный data root для безопасного сравнения. Ошибки и диагностика идут в stderr. Контракт stdout существующего `digest` сохраняется: только ISO-неделя.

Режимы интеграции в конфигурации:

- `off`: прежняя семантика отчёта; корректное чтение по глобальному архиву после переноса даты сохраняется.
- `shadow`: рассчитывать предложения и diff, рабочие индексы/выпуски остаются прежними.
- `enforce`: применять подтверждённый реестр и разрешённые точные правила, строить канонические индексы.

`digest` читает реестр и не принимает новые identity-решения. Если входы изменились и требуется reconcile, завершаться с понятным указанием обновить реестр локальным инструментом; не переключаться молча на legacy. `collect` в enforce выполняет reconcile тем же движком. Смена правил и ручных решений применяется отдельным `plan/apply`, а не неожиданно при рендере недели.

## 10. Запись, ошибки и workflows

Сначала сохранять изменившиеся наблюдения и совместимое представление источника. Затем валидировать и строить identity/canonical результат во временном каталоге. Отдельные файлы записывать через atomic rename; согласованность набора проверять manifest с fingerprints входов и выходов. Manifest публиковать последним. Падение между файлами должно обнаруживаться и устраняться повторным rebuild; один rename файла не объявлять транзакцией всего дерева.

При ошибке identity не терять успешно собранные исходные версии. Сохранять их и состояние успешного fetch, а состояние последнего успешного canonical build учитывать отдельно. Старые derived data не маркировать свежими. Автоматическая публикация выпуска при несогласованном manifest запрещена.

Текущий collect workflow прекращает работу при ненулевом exit code до commit. На этапе интеграции изменить его контракт: различать результат сохранения source data и результат canonical build. При успешном сохранении источников и ошибке дедупликации workflow должен иметь возможность закоммитить только подтверждённые исходные изменения и manifest наблюдений, затем завершиться ошибкой и отправить существующее failure-уведомление. Не коммитить частично построенный canonical набор.

Сохранить общую `concurrency: archive`. После resync повторять сбор/reconcile из нового состояния, не переносить устаревший план поверх нового реестра. Retry должен переоценивать fingerprints. В workflow добавить явные наборы путей для source и derived данных вместо безусловного `git add data` в ветке частичного успеха.

Полный исторический rebuild выполнять отдельным локальным процессом или отдельным maintenance-действием без Telegram-рассылки. Существующий digest workflow уведомляет об успешном выпуске, поэтому его нельзя просто вызвать циклом для всех старых недель.

| `internal/score` | Однократный расчёт на каноническом входе |
| `internal/render` | Единые IDs, provenance, новые подписи счётчиков |
| `internal/config`, `config.yaml` | Режим и версии политик, пути решений |
| `Makefile`, `.github/workflows` | CLI targets, проверки, commit scope, retry и maintenance rebuild |
| `testdata/dedup` | Положительные, отрицательные и конфликтные примеры |

Не вводить общий framework плагинов ради пяти текущих типов источников: достаточно явных возможностей и небольших функций адаптеров. Решение о разделении пакетов уточнить по направлению зависимостей, не создавать циклы `archive ↔ dedup ↔ model`.

## 13. Проверки и критерии качества

| Сценарий | Ожидаемый результат |
| --- | --- |
| Повтор одного fetch | Нет новой ревизии, смены ID и файлового diff |
| Стабильный ID, исправленное начало в другой ISO-неделе/году | Один source record и canonical ID; обе недели пересчитаны |
| AWS 22 updates и их 16-update подмножество | После подтверждения одна группа, 22 уникальных updates, оба свидетельства доступны |
| AWS новая версия с новым resolved update | История сохранена, завершение учитывается по evidence |
| AWS то же имя сервиса и заголовок после закрытого события | Независимые инциденты без достаточного нового доказательства |
| Одинаковый body в разных регионах | Не объединять только по тексту |
| Общий URL AWS | Не создаёт объединения |
| Несколько записей с одним шаблонным update | Review-only; нет автоматической группы |
| A похож на B, B похож на C, A запрещено объединять с C | Запрет соблюдён, цепочка не склеивается |
| Один update ID, текст исправлен | Один логический update с сохранёнными ревизиями |
| Один timestamp, разные body без ID | Сообщения сохраняются отдельно |
| Порядок старых snapshots неизвестен | Явный конфликт, нет придуманной актуальности |
| Resolved, затем явное повторное открытие | Порядок подтверждённых обновлений важнее ранга статуса |
| Ручной split | Нет потери участников; старые aliases разрешаются корректно либо явно неоднозначны |
| Новый участник с более ранней датой | Существующий canonical ID не меняется |
| Конфликт ручных решений или неизвестная ссылка | Apply прекращается с указанием ошибки |
| Удаление записи из входного фида | Архив и членство сохраняются |
| Прерывание записи derived файлов | Несогласованность обнаруживается; повторный rebuild восстанавливает набор |
| Источники сохранены, canonical build завершился ошибкой | Исходные изменения доступны для отдельного commit, выпуск не публикуется |
| Смена порядка файлов и записей | Побайтово одинаковый результат |
| Только изменение часов | Нет служебного churn; реальное изменение score ongoing-инцидента учитывается |
| Пустая после merge неделя | Корректный пустой индекс, отсутствие старого дубля |
| Повтор исторического rebuild | Нет повторных уведомлений и необъяснимого diff |

Использовать unit-тесты правил, golden-тесты отчётов и integration-тесты полного цикла на временных каталогах. Для permutation/idempotence и ограничений membership уместны property-тесты. Синтетические сценарии маркировать как синтетические, не выдавать за захваченные ответы вендоров.

Основные команды проверки: `make test` и `make lint`. Тесты аудитора входят в
общий запуск, включая `-race`. Для нового CLI добавлены integration-проверки
неизменности архива и выпусков, повторяемости отчёта и защиты путей вывода.

Качество оценивать отдельно: точность автоматических объединений, найденные дубли в размеченном наборе, доля review-only кандидатов, число конфликтов и изменение недельных результатов. Число кандидатов не служит целевым KPI. Любое известное ложное auto-объединение блокирует включение соответствующего правила до исправления; ноль ошибок на небольшом наборе не доказывает универсальную точность.

## 14. Внедрение, откат и ограничения

Внедрение выполнено последовательно: read-only audit, fixtures, схемы/реестр, observations, shadow-сравнение, полная миграция на копии, проверка и локальное включение enforce. Публикация остаётся отдельным действием.

Перед включением сохранить baseline commit, реестр, решения, конфигурацию и версию правил. Для воспроизведения исторического выпуска нужны также соответствующий архив и значение `-now`: применение сегодняшних данных к старой неделе является пересмотром истории, а не точным воспроизведением прежнего выпуска.

Откат выполнять отдельно по слоям: выключить enforce, сохранить версии источников и реестр для расследования, восстановить выбранную версию решений/правил, затем пересобрать нужные derived файлы. Старый бинарник не обязан понимать новую раскладку архива после исправления недели; rollback должен использовать совместимый загрузчик либо полностью восстановленный согласованный baseline в отдельном checkout.

При ложном объединении добавить решение о разделении, пересчитать реестр и обе затронутые недели, проверить старые ссылки. Физически удалять source snapshots для исправления identity не требуется. Если неверный выпуск уже опубликован, исправление и повторное уведомление — отдельное редакционное действие.

Ограничения остаются видимыми: часть истории потеряна до начала сбора, начало AWS приблизительное, некоторые статусы устарели, разные вендоры по-разному дробят аварии. Итоговый счётчик означает «инциденты после дедупликации собранных сообщений по версии правил», а не число всех уникальных аварий в мире.

Реализация считается завершённой, когда для каждой отображаемой группы можно ответить: из каких записей она собрана, почему они объединены, откуда взяты поля, как воспроизвести результат и как отменить решение без потери свидетельств.


## 15. Уточнения после полного прогона

- 23 исходных записи уже содержали `resolved_at < started_at`, включая raw.
  Слепое исправление даты создало бы выдуманную длительность. Добавлен
  `field_override: duration_unknown` с value `true`, pins текущих snapshots,
  автором Codex и evidence; даты сохранены, длительность выводится как unknown,
  её вклад в score равен нулю. Новое изменение evidence требует повторного review.
- 21 запись содержит одинаковые названия разных компонентов. Raw содержит
  различные component IDs, поэтому схлопывание по имени отменено; исходная
  кратность сохранена и проверена тестом. Формула score не менялась.
- Canonical JSON хранит поля внутри `fields`, ссылки в `sources`; отображаемые
  индексы получают `canonical` metadata. `start_quality` бывает vendor_reported,
  first_observed_update или editorial_override; неизвестная длительность —
  отдельный флаг, не выдуманная дата начала.
- Build собирает набор артефактов в памяти, пишет файлы atomic rename и manifest
  последним. Общей файловой транзакции и автоматического снятия stale lock нет.
- Смена порядка source rows меняет fingerprint физических входов; semantic
  canonical data и назначенные IDs от этого не меняются. Повтор идентичных входов
  с одинаковым now побайтово воспроизводим.
- Четыре явно последующих задачи остаются вне семи этапов: межвендорские
  редакционные связи, UI review, импорт всей Git-истории и fuzzy matching.
