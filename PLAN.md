# weekly-incident — план реализации

Дата составления: 2026-08-18. Все приведённые здесь замеры фидов сделаны в этот день, они датированы и подлежат перепроверке при расхождении с реальностью.

## 1. Что это

Публичный Go-репозиторий, который раз в сутки собирает инциденты со статус-страниц тринадцати вендоров в версионируемый JSON-архив, а раз в неделю строит из архива факт-шит для человека. Продукт проекта — еженедельные материалы, которые автор пишет сам на своих площадках. Код ничего не сочиняет и не обращается к LLM: он собирает, нормализует, ранжирует и раскладывает по файлам.

Граница проведена жёстко: детерминированный сбор внутри репозитория, осмысление снаружи. Из этого следует, что весь пайплайн воспроизводим, тестируем без сети и не требует ни одного API-ключа, кроме токена для `notiflow`.

## 2. Зафиксированные решения

| Решение | Выбор | Почему |
|---|---|---|
| Продукт | Выпуски, код — обвязка | Агрегаторов статус-страниц много, редакторского разбора на русском нет |
| Язык | Go | Прецедент в `srekit` и `gonewszer`, быстрая сборка в CI, RSS/JSON/UTF-16 стандартной библиотекой |
| LLM | Снаружи пайплайна | Неудачный промпт стоит один прогон генерации, а не повторный обход вендоров |
| Частота | Сбор ежедневно, выпуск еженедельно | Глубина фида Cloudflare — 20 дней, недельный сбор оставляет запас всего в две пропущенные недели |
| Отбор | Дайджест плюс герой недели, выбирает автор | Скор ранжирует и объясняет порядок, но не решает |
| Источники | 13, Azure исключён | У Azure нет машиночитаемой истории |
| Публикация | Только факты со ссылкой на первоисточник | Факты не охраняются, формулировки вендора охраняются |
| Репозиторий | Публичный | Данные не секретны, черновики автор ведёт вне репозитория |
| Архив | Накопительный merge, только upsert | Пагинации у Statuspage нет, исчезновение из фида означает вытеснение, а не отмену |
| Формат | JSON для данных, YAML для конфига | Стабильный диff, `encoding/json` в стандартной библиотеке |
| Тулинг | Makefile, стандартная библиотека плюс `yaml.v3` | Минимум зависимостей в проекте, живущем в cron |
| Лицензия | MIT на код, оговорка об источниках на данные | Автор не является правообладателем собранных фактов |

## 4. Модель данных

### 4.1 Канонические типы

Пакет `internal/model`. Все времена — UTC, сериализуются в RFC 3339. Все строковые поля — на английском, ровно как у вендора: нормализация переводом убила бы поиск по архиву.

```go
package model

type Impact string

const (
	ImpactNone     Impact = "none"
	ImpactMinor    Impact = "minor"
	ImpactMajor    Impact = "major"
	ImpactCritical Impact = "critical"
	ImpactUnknown  Impact = "unknown"
)

type Status string

const (
	StatusInvestigating Status = "investigating"
	StatusIdentified    Status = "identified"
	StatusMonitoring    Status = "monitoring"
	StatusResolved      Status = "resolved"
	StatusPostmortem    Status = "postmortem"
	StatusUnknown       Status = "unknown"
)

type Update struct {
	NativeID  string    `json:"native_id,omitempty"`
	Status    Status    `json:"status"`
	Body      string    `json:"body"`
	CreatedAt time.Time `json:"created_at"`
}

type Incident struct {
	Key             string          `json:"key"`
	Vendor          string          `json:"vendor"`
	NativeID        string          `json:"native_id"`
	Title           string          `json:"title"`
	URL             string          `json:"url"`
	Impact          Impact          `json:"impact"`
	Status          Status          `json:"status"`
	StartedAt       time.Time       `json:"started_at"`
	ResolvedAt      *time.Time      `json:"resolved_at,omitempty"`
	DurationMinutes *int            `json:"duration_minutes,omitempty"`
	Components      []string        `json:"components"`
	Updates         []Update        `json:"updates"`
	FirstSeenAt     time.Time       `json:"first_seen_at"`
	Raw             json.RawMessage `json:"raw"`
}
```

`Key` — `<vendor>/<native_id>`, единственный ключ merge во всём проекте. `Raw` хранит исходный объект вендора целиком, без обрезки: он весит копейки и спасает от ошибок нормализации, обнаруженных задним числом. `FirstSeenAt` ставится при первой записи и больше не меняется.

Поля «когда видели в последний раз» в модели намеренно нет. Оно менялось бы каждый прогон и переписывало бы все файлы ежедневно, превращая историю архива в шум и делая невозможным отличить настоящее обновление от сердцебиения крона.

`Raw` канонизируется при нормализации: payload вендора перекладывается через `map` с сортировкой ключей и без незначащих пробелов. Без этого вендор, поменявший порядок ключей в ответе или включивший pretty-print, переписал бы все свои файлы, не изменив ни одного факта. Числа декодируются через `json.Number`, чтобы большие целые не превратились в float.

`DurationMinutes` вычисляется только когда `ResolvedAt` не пуст. Для открытого инцидента поле отсутствует, а не равно нулю: разница между «шёл ноль минут» и «ещё идёт» существенна для скора.

### 4.2 Маппинг Statuspage

Схема одна на десять вендоров. Источник — массив `incidents[]`.

| Поле модели | Источник | Правило |
|---|---|---|
| `NativeID` | `id` | как есть |
| `Title` | `name` | как есть |
| `URL` | `shortlink` | если пусто — `page.url + "/incidents/" + id`; поле `shortlink` присутствует не у всех вендоров |
| `Impact` | `impact` | значения совпадают с каноническими: `none`, `minor`, `major`, `critical` |
| `Status` | `status` | `investigating`, `identified`, `monitoring`, `resolved`, `postmortem` совпадают |
| `StartedAt` | `started_at` | если пусто — `created_at` |
| `ResolvedAt` | `resolved_at` | `null` для открытых |
| `Components` | `components[].name` | сохраняется только имя |
| `Updates` | `incident_updates[]` | `id`, `status`, `body`, `created_at` |
| `Raw` | весь объект инцидента | без изменений |

### 4.3 Маппинг Slack

Источник — массив объектов верхнего уровня. Поля: `id` (число), `title`, `type`, `status`, `url`, `date_created`, `date_updated`, `notes[]`, `services[]`.

| Поле модели | Источник | Правило |
|---|---|---|
| `NativeID` | `id` | приводится к строке |
| `Title` | `title` | как есть |
| `URL` | `url` | как есть |
| `Impact` | — | Slack не сообщает impact, ставится `unknown` |
| `Status` | `status` | `active` → `investigating`, `resolved` → `resolved` |
| `StartedAt` | `date_created` | смещение `-07:00`, приводится к UTC |
| `ResolvedAt` | `date_updated` | только если `status == "resolved"` |
| `Components` | `services[]` | массив строк, например `["Messaging", "Workspace/Org Administration"]` |
| `Updates` | `notes[]` | `body`, `date_created`; статуса у заметки нет, ставится `unknown` |

Тела заметок приходят в HTML (`<p>...</p>`). Теги вырезаются при нормализации, исходный HTML остаётся в `Raw`.

### 4.4 Маппинг GCP

Источник — массив объектов. Поля: `id`, `number`, `begin`, `created`, `end`, `modified`, `external_desc`, `updates[]`, `most_recent_update`, `status_impact`, `severity`, `service_key`, `service_name`, `affected_products[]`, `uri`, `currently_affected_locations`, `previously_affected_locations`.

| Поле модели | Источник | Правило |
|---|---|---|
| `NativeID` | `id` | как есть |
| `Title` | `external_desc` | обрезается до первого предложения или 200 рун, полный текст остаётся в `Raw` |
| `URL` | `uri` | относительный, префиксуется `https://status.cloud.google.com/` |
| `Impact` | `severity` плюс `status_impact` | `high` → `critical`; `medium` → `major`; `low` → `minor`; при `status_impact == "SERVICE_INFORMATION"` принудительно `none` |
| `Status` | `end` | пусто → `investigating`, иначе `resolved` |
| `StartedAt` | `begin` | не `created`: `begin` — это фактическое начало воздействия |
| `ResolvedAt` | `end` | как есть |
| `Components` | `affected_products[].title` | если пусто — `[service_name]` |
| `Updates` | `updates[]` | `when` → `CreatedAt`, `text` → `Body`, `status` → `Status` через ту же таблицу |

Тексты апдейтов приходят в Markdown с экранированными решётками (`## \# Incident Report`). Оставляются как есть, разэкранирование — задача рендера, не сбора.

### 4.5 Маппинг AWS RSS

Самый неприятный источник: фид отдаёт не инциденты, а плоский поток апдейтов.

Первая гипотеза, что событие закодировано в `guid`, оказалась неверной, и это проверено на живом фиде 2026-08-18: epoch внутри `guid` совпадает секунда в секунду с `pubDate` самой записи, у всех пятидесяти записей без исключения. Группировка по паре «сервис плюс epoch» дала бы по одному инциденту на каждый апдейт. На деле `guid` несёт ровно один полезный сигнал — ключ сервиса:

```
https://status.aws.amazon.com/#directconnect-eu-central-1_1787025679
                               └──── service_key ────┘ └ время этой записи ┘
```

Алгоритм. Записи собираются по `service_key` и сортируются по возрастанию времени. Цепочка разрывается в двух случаях: сразу после записи с маркером завершения (`[RESOLVED]` в заголовке либо префикс `Service is operating normally`) и при разрыве во времени больше 24 часов. Оба правила нужны: AWS ставит маркер завершения не всегда, и в замеренном фиде две цепочки из трёх закрыты только разрывом.

Порог в 24 часа взят из формы реальных данных, а не из головы. Внутри события AWS публикует апдейты каждые 1-7 часов, наибольший наблюдённый внутренний разрыв — 6.8 часа. Между соседними событиями одного и того же сервиса разрыв составил 1383 часа. Порог лежит на два порядка ниже второго и втрое выше первого.

`NativeID` — первые 16 шестнадцатеричных знаков SHA-256 от строки `service_key + "_" + <epoch первой видимой записи цепочки>`.

| Поле модели | Правило |
|---|---|
| `Title` | заголовок последней записи цепочки, с обрезкой префиксов `Service is operating normally:`, `Informational message:`, `Service disruption:`, `Service degradation:`, `Service impact:` и маркера `[RESOLVED]` |
| `URL` | `https://health.aws.amazon.com/health/status` — стабильной ссылки на событие фид не даёт, собственный `<link>` записи всегда указывает на корень статус-страницы |
| `Impact` | `unknown`: AWS не сообщает уровень воздействия машиночитаемо |
| `Status` | `resolved`, если в цепочке есть маркер завершения, иначе `investigating` |
| `StartedAt` | время первой записи цепочки |
| `ResolvedAt` | время последней записи цепочки, если статус `resolved` |
| `Components` | `[service_key]`, например `directconnect-eu-central-1` |
| `Updates` | по одному на каждую запись цепочки: `description` в `Body`, `pubDate` в `CreatedAt` |
| `Raw` | JSON-массив исходных `<item>` цепочки целиком |

Отдельная засада с временем: `pubDate` приходит в виде `Mon, 17 Aug 2026 21:01:19 PDT`. Аббревиатуры зон Go разбирает ненадёжно, `time.RFC1123Z` тут не подходит. Используется своя таблица (`PST → -0800`, `PDT → -0700`, `UTC → +0000` и остальные американские) с подстановкой смещения перед разбором. Неизвестная аббревиатура — явная ошибка, никогда не молчаливый UTC: тихая подмена сдвинула бы инцидент на несколько часов и испортила бы и окно недели, и длительность.

Ограничение идентификатора. AWS не публикует стабильного идентификатора события, поэтому ключ выводится из первой записи цепочки, видимой в фиде. Если цепочка окажется на границе окна в пятьдесят записей и её самые ранние апдейты вытеснятся, пока поздние ещё видны, ключ пересчитается и событие ляжет в архив вторым экземпляром. Событие в фиде занимает до двадцати записей из пятидесяти, так что вероятность не нулевая. Осознанно принято: дубль в архиве дешевле, чем усложнение merge ради источника, который и так может исчезнуть в любой день.

Эндпоинт `https://health.aws.amazon.com/public/currentevents` не используется: он отдаёт снимок текущего состояния (на замере — три события) и для недельного окна бесполезен. Также он приходит в UTF-16, что отдельно неудобно.

## 5. Конфигурация

Единственный файл `config.yaml` в корне, версионируется вместе с кодом. Никакого переопределения через переменные окружения, кроме секретов `notiflow`.

```yaml
user_agent: "weekly-incident/0.1 (+https://github.com/jtprogru/weekly-incident)"

http:
  timeout: 30s
  retries: 3
  backoff_base: 2s

collect:
  fail_threshold: 0.5   # красный job, если недоступно больше половины источников
  gap_warn_days: 14     # предупреждение, если в архиве разрыв длиннее

digest:
  # Инцидент проходит порог, если выполнено ЛЮБОЕ из двух условий.
  # Значение выверено на живой неделе 2026-W33 (48 инцидентов по 13 источникам):
  # 30 мин -> 36 выше порога, 60 -> 28, 120 -> 22, 180 -> 16, 240 -> 15.
  # Медианный инцидент длится 1-3 часа, поэтому порог в 30 минут не фильтрует почти ничего.
  min_duration_minutes: 120
  min_impact: major
  brief_top_n: 5
  brief_body_limit: 800 # рун на тело апдейта в brief.md

sources:
  - vendor: github
    kind: statuspage
    url: https://www.githubstatus.com/api/v2/incidents.json
    weight: 1.5
  - vendor: cloudflare
    kind: statuspage
    url: https://www.cloudflarestatus.com/api/v2/incidents.json
    weight: 1.8
  - vendor: aws
    kind: aws-rss
    url: https://status.aws.amazon.com/rss/all.rss
    weight: 2.0
  # ... остальные десять по тому же образцу
```

`weight` — вес вендора в скоре. Смысл в редакторской значимости: падение AWS интереснее аудитории, чем падение DigitalOcean, при равной длительности.

## 6. Архив

### 6.1 Раскладка

```
data/2026/W34/github.json        все инциденты GitHub, начавшиеся на этой ISO-неделе
data/2026/W34/cloudflare.json
data/2026/W34/...
data/2026/W34/index.json         сводка недели со скором и статусами источников
weeks/2026-W34/digest.md         факт-шит для человека
weeks/2026-W34/brief.md          сжатый контекст для передачи в LLM
```

Файл на вендора внутри недели, а не один общий: диff читается, сбой одного источника не трогает файлы остальных. Неделя определяется по `StartedAt` инцидента в ISO-нумерации, зона UTC. Инцидент, начавшийся в воскресенье и закончившийся в понедельник, целиком принадлежит неделе начала.

Каждый вендорский файл — JSON-массив `Incident`, отсортированный по `StartedAt` по возрастанию, поля объектов идут в порядке объявления структуры, отступ два пробела, файл заканчивается переводом строки. Это делается ради стабильного диффа: одинаковый вход обязан давать побайтово одинаковый выход, иначе ежедневный коммит превратится в шум.

### 6.2 Семантика merge

Только upsert по `Key`, удалений не бывает.

При каждом прогоне для каждого инцидента из фида: если ключа в архиве нет — запись создаётся, `FirstSeenAt` и `LastSeenAt` ставятся в момент прогона. Если ключ есть — поля перезаписываются свежими значениями, `FirstSeenAt` сохраняется, `LastSeenAt` обновляется, массив `Updates` заменяется целиком (вендор — источник истины по своим апдейтам), `Raw` перезаписывается.

Инцидент, пропавший из фида, остаётся в архиве нетронутым: исчезновение означает вытеснение из окна в пятьдесят записей, а не отмену события. Это же правило делает бессмысленной попытку пересобирать фиксированное окно в восемь недель — глубина фида Cloudflare составляет двадцать дней, и требуемых пятидесяти шести дней там просто нет. Поздние апдейты и постмортемы подтягиваются, пока инцидент остаётся в окне вендора, чего достаточно: постмортемы приходят в первые дни, а не через месяц.

Инцидент, начавшийся на прошлой неделе и получивший апдейт на этой, обновляется в файле своей недели. Прогон, соответственно, пишет не только в текущую неделю.

Повторно увиденный инцидент — это не изменение. Прогон сравнивает сериализованные байты записи с тем, что уже лежит в архиве, и если они совпадают, файл не переписывается вообще. Без этого правила каждый ежедневный прогон трогал бы все недели, до которых дотягиваются фиды: на первом реальном запуске их оказалось 72, с 2019-W19 по 2026-W34. Проверено: два прогона подряд оставляют архив побайтово одинаковым, меняется только `state.json`.

### 6.3 index.json

```go
type SourceStatus struct {
	Vendor        string    `json:"vendor"`
	OK            bool      `json:"ok"`
	Error         string    `json:"error,omitempty"`
	FetchedAt     time.Time `json:"fetched_at"`
	IncidentsSeen int       `json:"incidents_seen"`
	ParseErrors   int       `json:"parse_errors"`
}

type IndexEntry struct {
	Key             string     `json:"key"`
	Vendor          string     `json:"vendor"`
	Title           string     `json:"title"`
	URL             string     `json:"url"`
	Impact          Impact     `json:"impact"`
	Status          Status     `json:"status"`
	StartedAt       time.Time  `json:"started_at"`
	ResolvedAt      *time.Time `json:"resolved_at,omitempty"`
	DurationMinutes *int       `json:"duration_minutes,omitempty"`
	Ongoing         bool       `json:"ongoing"`
	Components      []string   `json:"components"`
	Score           Score      `json:"score"`
	AboveThreshold  bool       `json:"above_threshold"`
}

type WeekIndex struct {
	Week        string         `json:"week"`
	From        time.Time      `json:"from"`
	To          time.Time      `json:"to"`
	GeneratedAt time.Time      `json:"generated_at"`
	Sources     []SourceStatus `json:"sources"`
	Incidents   []IndexEntry   `json:"incidents"`
}
```

`index.json` полностью производен от вендорских файлов и пересобирается с нуля — но только для тех недель, которые прогон реально изменил. Недели без изменений сохраняют уже лежащий индекс, иначе ежедневный сбор трогал бы все 72 недели, до которых дотягиваются фиды.

У самого индекса есть поле `GeneratedAt`, и оно меняется каждый прогон. Поэтому запись индекса тоже под защитой: файл переписывается, только если изменилось что-то кроме этой метки. Вызывающему возвращается то, что фактически лежит на диске, и рендер цитирует именно эту метку, а не свежепридуманную. Без этого перерендер устоявшейся недели давал бы коммит с диффом из одного timestamp.

Индекс существует, чтобы рендеру не читать весь `Raw` ради построения таблицы.

## 7. Скоринг

```go
type Score struct {
	Value      float64 `json:"value"`
	Duration   int     `json:"duration_minutes"`
	Components int     `json:"components"`
	Weight     float64 `json:"vendor_weight"`
}
```

`Value = Duration * max(1, Components) * Weight`.

Для открытого инцидента длительность считается от `StartedAt` до момента генерации выпуска, и в `digest.md` он помечается как `ongoing`. Все три множителя печатаются рядом со строкой в таблице: порядок сортировки должен быть объясним читателю без чтения кода.

Скор ранжирует и подсказывает, но не решает. Героя недели выбирает автор, никакого файла с курированием в v1 нет.

## 8. Рендер

### 8.1 digest.md

Заголовок с номером недели и датами окна. Затем строка сводки: сколько инцидентов всего, сколько прошло порог, какие источники были недоступны. Затем таблица инцидентов выше порога, отсортированная по скору по убыванию: вендор, заголовок со ссылкой, начало в UTC, длительность, компоненты, скор с разложением на множители. Затем таймлайны — для каждого инцидента выше порога список апдейтов с временем и текстом. Затем строка `ещё N инцидентов ниже порога` со свёрнутым списком в одну строку на инцидент. В конце — блок статусов источников, включая строки вида `warning cloudflare: fetch failed`.

Порог: инцидент проходит, если `DurationMinutes >= min_duration_minutes` **или** `Impact` не ниже `min_impact`. Дизъюнкция, а не конъюнкция: короткое критическое падение интереснее длинного minor.

Всё содержимое на английском.

### 8.2 brief.md

Топ-`brief_top_n` по скору. Для каждого — заголовок, вендор, ссылка, окно времени, длительность, компоненты и апдейты с телами, обрезанными до `brief_body_limit` рун по границе руны с добавлением многоточия. Ниже — однострочный перечень остальных инцидентов выше порога. Никакой сети, никаких вызовов LLM, только сортировка и обрезка.

### 8.3 summary.txt

Три-четыре строки: номер недели, сколько инцидентов всего и сколько выше порога, топ-3 с вендором, заголовком и длительностью. Это то, что workflow отдаёт в `notiflow`, чтобы уведомление в личку было содержательным, а не «job succeeded».

## 9. Взаимодействие компонентов

```
config.yaml
     │
     ▼
cmd/collect ──► internal/source ──► []model.Incident ──► internal/archive
                  statuspage.go        (канонические)        upsert по Key
                  slack.go                                        │
                  gcp.go                                          ▼
                  awsrss.go                             data/YYYY/Wnn/<vendor>.json
                       │                                          │
                       ▼                                          ▼
                 SourceStatus ────────────────────────►  data/YYYY/Wnn/index.json
                                                                  │
config.yaml ──────────────────────────────────────────────────────┤
                                                                  ▼
                                            cmd/digest ──► internal/score
                                                                  │
                                                                  ▼
                                                        internal/render
                                                                  │
                                            ┌─────────────────────┴──────────┐
                                            ▼                                ▼
                                  weeks/YYYY-Wnn/digest.md      weeks/YYYY-Wnn/brief.md
```

`cmd/collect` — единственный компонент, ходящий в сеть. `cmd/digest` в сеть не ходит вовсе: читает архив, обновляет `index.json` этой недели и пишет три файла в `weeks/`. Отсюда его детерминированность — любую прошлую неделю можно перерендерить с другим порогом или другой формулой скора, ничего не перекачивая.

Неделю, которую он отрендерил, `cmd/digest` печатает в stdout одной строкой; человекочитаемый лог идёт в stderr. Это нужно workflow, чтобы не угадывать неделю по содержимому каталога.

Интерфейс источника:

```go
package source

// Result отделяет удачно разобранные инциденты от счётчика битых записей:
// одна неразобранная запись не должна ронять источник целиком.
type Result struct {
	Incidents   []model.Incident
	ParseErrors int
}

type Source interface {
	Vendor() string
	Fetch(ctx context.Context, f *Fetcher) (Result, error)
}

// Fetcher держит User-Agent и политику ретраев, чтобы каждый парсер не
// повторял их у себя.
func New(cfg config.Source) (Source, error) // диспетчер по полю kind
```

Добавление вендора со схемой Statuspage — строка в `config.yaml`. Добавление вендора с новой схемой — новый файл в `internal/source` и новая ветка в диспетчере.

## 10. Workflows

`collect.yml` — ежедневно в 06:00 UTC плюс `workflow_dispatch`. Собирает, мержит в архив, коммитит в `main`, если рабочее дерево изменилось. При провале — уведомление через `notiflow` в личку.

`digest.yml` — по понедельникам в 07:00 UTC плюс `workflow_dispatch`. Сеть не трогает: читает архив за предыдущую ISO-неделю, пишет `digest.md` и `brief.md`, коммитит, шлёт `notiflow` с топ-3 недели и ссылкой на `digest.md` этой недели. `parse_mode: none`, потому что текст содержит точки, скобки и URL, на которых MarkdownV2 у Telegram падает.

`ci.yml` — на push и pull request: `go vet`, `golangci-lint`, `go test ./...`.

Отдельная забота: GitHub глушит cron в репозиториях без активности шестьдесят дней. Ежедневный коммит данных сам по себе служит активностью, так что расписание не заснёт, пока сбор работает. Если же сбор сломается, расписание умрёт следом, поэтому проверка разрыва в архиве и алерт в `notiflow` обязательны, а не желательны.

## 11. Ошибки и устойчивость

Три попытки на источник с экспоненциальной задержкой от `backoff_base`. Недоступный источник помечается в `SourceStatus` с текстом ошибки и не прерывает прогон. Job краснеет, только если доля недоступных источников превысила `fail_threshold`, то есть проблема, скорее всего, на своей стороне, а не у вендоров.

Ошибка разбора отдельной записи не роняет источник: запись пропускается, счётчик `ParseErrors` растёт, в `digest.md` появляется предупреждение. Это важно для AWS RSS, где формат заголовков и зон не гарантирован никем.

Проверка разрыва: если между последним и предпоследним успешным сбором прошло больше `gap_warn_days`, в лог и в `notiflow` уходит предупреждение о вероятной потере данных. Восстановить пропущенное неоткуда — пагинации нет.

`User-Agent` осмысленный, со ссылкой на репозиторий. Запросы к источникам последовательны либо с ограничением параллелизма: тринадцать запросов раз в сутки не требуют никакой агрессии.

## 12. Тесты

Golden-файлы в `testdata/` по одному на каждый из четырёх типов источника, снятые с живых эндпоинтов и зафиксированные. Тесты парсеров работают без сети и проверяют полный маппинг в канонический вид, включая разбор зон `PST`/`PDT` у AWS и склейку апдейтов по `guid`.

Отдельно тестируются: идемпотентность merge (два прогона на одном входе дают побайтово одинаковый архив), стабильность сериализации (сортировка ключей и записей), вычисление границ ISO-недели на переходах через год, пороговая логика рендера.

Всё остальное — склейка строк, покрытия не требует.

## 15. Известные ограничения

Azure отсутствует: машиночитаемой истории у него нет, RSS отдаёт только активные события и на замере был пуст.

Плановые работы не собираются: `scheduled-maintenances.json` — отдельный эндпоинт с иной семантикой, а материала для выпуска почти не даёт. Если плановая работа переросла в аварию, вендор заводит обычный инцидент.

Пагинации у Statuspage нет, глубина упирается в пятьдесят инцидентов. Данные за период до первого запуска восстановить неоткуда, и пропущенные прогоны создают невосполнимые пробелы.

`status.aws.amazon.com/rss/all.rss` и `slack-status.com/api/v2.0.0/history` недокументированы.

Идентификатор события AWS выводится из первой видимой записи цепочки, потому что своего у AWS нет. Цепочка, попавшая на границу окна в пятьдесят записей, может продублироваться в архиве.

Начало события AWS — это время первого апдейта, попавшего в фид, а не фактическое начало воздействия. Настоящее начало AWS указывает только прозой в тексте итогового сообщения («Starting August 14 7:33 PM PDT»), и разбирать его регуляркой ненадёжно.

Slack и AWS не сообщают уровень воздействия машиночитаемо, у них `Impact` всегда `unknown`, что занижает их место в сортировке при `min_impact`-условии. Порог по длительности для них работает нормально.

Заголовок инцидента GCP синтезируется из `external_desc` обрезкой, полный текст лежит в `Raw`.

Datadog, Atlassian и GCP на замере дали ноль инцидентов за неделю. Источники низкоурожайные, но остаются: GCP раз в квартал приносит развёрнутый постмортем, ради которого всё и затевалось.

Права на исходные формулировки вендоров принадлежат вендорам. В публикацию идут факты со ссылкой на первоисточник, дословные цитаты — короткие и в кавычках.

## 16. Что изменилось при реализации

План писался до того, как код увидел живые фиды. Шесть решений пришлось поменять, и все шесть — из-за данных, а не из-за вкуса.

**Группировка AWS.** План предполагал, что epoch в `guid` — это начало события, и группировал по паре «сервис плюс epoch». На живом фиде epoch совпал секунда в секунду с `pubDate` самой записи, у всех пятидесяти. Такая группировка дала бы пятьдесят инцидентов вместо пяти. Заменено на группировку по сервису с разрезанием по маркеру завершения и по разрыву в 24 часа. Подробности в разделе 4.5.

**Поле «когда видели в последний раз» удалено.** Оно меняется каждый прогон и переписывало бы весь архив ежедневно. Вместо него — сравнение сериализованных байтов: повторно увиденный без изменений инцидент не трогает файл.

**`Raw` канонизируется.** Иначе изменение порядка ключей на стороне вендора выглядело бы как изменение данных.

**Порог поднят с 30 до 120 минут.** На реальной неделе 30 минут пропускали 36 инцидентов из 48. Медиана длительности — 1-3 часа, так что низкий порог не фильтровал ничего. Цифры по всем вариантам — в комментарии в `config.yaml`.

**Пакета `internal/notify` нет.** Уведомления делает шаг `notiflow` в самом workflow. Тащить телеграм-секреты в Go ради двух вызовов не за чем.

**У источника в интерфейсе появился тип `Result`.** Счётчик неразобранных записей нужно было вернуть наверх, не смешивая его с ошибкой всего источника.

Кроме того, найдено то, чего в плане не было: `status.anthropic.com` редиректит на `status.claude.com` (в конфиге сразу конечный адрес), а первый реальный сбор забрал 511 инцидентов за 72 недели, с 2019-W19 по 2026-W34 — фиды тихих вендоров вроде Atlassian тянутся на годы назад. Весь архив занял 5 МБ.

## 17. Что изменило ревью

Двухосевое ревью (стандарты против `CLAUDE.md`, спека против этого файла) нашло три настоящие поломки и несколько расхождений. Все закрыты.

**`index.json` был недетерминирован.** `cmd/digest` переписывал его безусловно, а `GeneratedAt` меняется каждый прогон. Два одинаковых рендера подряд давали разный хеш файла, то есть workflow коммитил бы дифф без единого факта — ровно то, от чего защищает весь остальной архив. Теперь `WriteIndex` сравнивает содержимое, игнорируя метку времени, и возвращает то, что фактически лежит на диске; `cmd/digest` пишет `digest.md`, `brief.md` и `summary.txt` только при реальном изменении.

**Workflow определял неделю по каталогу.** `ls -1d weeks/*/ | sort | tail -1` брал самый свежий каталог на диске, а не отрендеренную неделю, поэтому ручной запуск на старую неделю уводил и summary, и сообщение коммита, и ссылку в телеграм. Теперь `cmd/digest` печатает неделю в stdout, workflow забирает её оттуда.

**Предупреждение о разрыве архива никуда не уходило.** Раздел 11 обещал «в лог и в notiflow», а на деле был только `log.Printf` в логах, которые никто не читает при зелёном job. Теперь `collect` умеет `-warning <path>`, workflow поднимает текст в `::warning::` и отдельным шагом шлёт его в личку. Заодно выяснилось, что `notiflow` не знает статуса `warning` (только success/failure/cancelled/skipped), а `parse_mode` по умолчанию MarkdownV2 и падает на точках, скобках и URL — оба уведомления переведены на `parse_mode: none`.

**Предупреждение о `ParseErrors` появилось в `digest.md`.** Раньше это была молчаливая цифра в колонке таблицы; теперь при ненулевом счётчике сверху выводится строка с именами вендоров и подсказкой перезахватить golden-файлы. Растущий счётчик означает, что вендор поменял схему и инциденты теряются.

**Мелкие чистки.** Разбор `-now` вынесен в `internal/clock` (был побайтово продублирован в обеих командах). Четыре структуры источников свёрнуты на общий `base`. `Source.Vendor()` удалён из интерфейса — в проде его никто не вызывал. `Stats.Weeks` стал `[]Week` вместо `[]string`, что убрало круг `Week → string → Week` с путём ошибки на собственных значениях. Убран посредник `dec := yaml.Unmarshal`, переименован `render.index` (имя конфликтовало с `index.json`), хардкод топ-3 в уведомлении стал именованной константой `summaryTopN` с объяснением, почему он не равен `BriefTopN`. Из док-комментария `internal/config` убрана ссылка на пакет `internal/notify`, которого не существует.

Формулировки этого плана тоже разошлись с кодом и поправлены по факту: порядок полей в JSON (не лексикографический, а порядок объявления структуры), пересборка индекса (только изменённые недели), `cmd/digest` (не только читает — ещё и пишет, но в сеть не ходит), ссылка в уведомлении (на `digest.md`, не на коммит), состав `IndexEntry` и вес Cloudflare в примере конфига.
